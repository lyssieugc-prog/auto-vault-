# GAME_SYSTEMS.md — Permanent Roblox Brainrot / Studded Game Standard
Version: 1.0 | Scope: ALL games generated by this vault

## Mission and input contract
Given only a game NAME and DESCRIPTION, plan and implement a complete, coherent Roblox game in the established bright brainrot/studded style. Adapt systems to the core loop; do not blindly paste irrelevant mechanics. If a user instruction conflicts with this document, ask only when it is genuinely consequential; otherwise treat explicit per-game instructions as overrides while preserving non-negotiables below. Never describe unfinished work as finished.

## Non-negotiable production pipeline
- **Blender owns ALL custom 3D content:** entire map, buildings, bases, set dressing, props, machines, collectibles, decorations, and game-specific assets. Model, UV, assign materials/textures, organize naming, and export in **batch**. Roblox Studio is for scene placement/import, assembly, lighting, terrain integration if absolutely required, scripts, UI, interactions, simulation, and testing. Do not replace Blender modeling with Part-built stand-ins presented as final art.
- **Studs are part of the visual language.** Maintain clearly visible intentional studs in map surfaces and model materials, including appropriately tiled/UV-authored textures where required. No generic flat plastic look. Keep scale/readability consistent and avoid dense studs on tiny details.
- **Preserve the user's existing style references and aesthetic rules**; references describe STYLE, not assets to copy. Do not change to a different aesthetic just to simplify implementation.
- **Figma-first for UI.** Design component library, interaction states, responsive layouts, screens and specifications in Figma; implement actual runtime UI in Roblox with reusable Luau modules. Figma is not the runtime UI.
- **Editor-visible result is mandatory.** Import/map objects remain visible in Studio Edit mode, correctly positioned and lighted. Supply a Studio preview method for screens and states without relying only on pressing Play (e.g., a clearly labeled preview hierarchy or Studio-editable ScreenGui previews and documented mock-data preview procedure). Explicitly distinguish editor preview from runtime validation.
- **Maximum 6 players per server** and **6 themed bases**, one claimable base per player. Spawn and ownership must remain correct after leaving/rejoining or server turnover. Define all six positions in Blender with consistent orientation and safe spawn zones. Configure experience server maximum to 6 in publishing/settings; verify it, not merely script an assumption.
- **Progressive bases:** each base visually expands/upgrades with in-game progression. Define at least a base starter stage and visible upgrades; number of levels and their requirements are game-specific. All stage meshes must be authored in Blender, imported in batches and toggled/placed by game logic.

## Core loop and progression
Create a design brief from the game name/description with: one-sentence fantasy; 15-second activity; 2–5-minute progression goal; 15–30-minute session goal; repeat/return hook; currency sinks; and which systems make sense. Prioritize a playable, satisfying core loop before additional content. Avoid progress blockers, useless currency or excessive UI interruption.

## Monetization: context-dependent Robux multiplier
- Provide one prominent, legible **x2 [RESOURCE]** purchase button on a left or right HUD rail, whichever avoids overlap with other core actions. Label RESOURCE from the primary gameplay loop (earnings, speed, luck, etc.) and disclose the exact effect.
- Sequential **owned multiplier tiers**: x2 → x4 → x8 → x16 → x32 → x64 → **x128 maximum**. Display owned tier, next tier, configured Robux price, and benefit. No tiers above x128.
- **Prices must rise each tier**, but do not invent production prices: keep product identifiers/prices in an explicit configuration that the user fills or approves. Never assume actual storefront Robux price from client-side constants; retrieve/validate authoritative price/product information as supported.
- Implement server-side receipt/entitlement processing appropriate to the chosen permanent-upgrade model; handle repeated, delayed, failed, or duplicate receipts idempotently. Persist permanent ownership. Test in a sandboxed purchase flow, no real charges.
- Balance economy around free players; offer meaningful non-paying progression. Prevent unintended stacking/exploits and display if other buffs multiply or add.

## Season 1 battle pass
- **50 tiers**, **free + paid premium** tracks, with a visible progress/XP bar, reward previews, claim status, current tier, and clear premium upgrade option.
- All rewards fit the game theme: cosmetics, collectible variants, trails, effects, currency, boosts, special base decorations or applicable companion items. Do not introduce pets/eggs just to fill rewards.
- Rewards require explicit claim or documented auto-claim behavior, persist correctly and never duplicate. Season boundaries, XP sources, XP curve, end date and premium price are configurable; do not invent a calendar end date or Roblox prices.
- Season UX: animated progress fill, reward reveal, 50-tier scroll/virtualization where useful, premium lock state, free rewards still claimable.

## First-time onboarding and retention
- **Visually animated themed loading screen** with progress indication reflecting real preloading states when possible; do not fake a forever progress bar. Provide skip/timeout fallback for slow assets. It transitions into the game smoothly.
- **First-join interactive guided tutorial:** arrows, highlights, short actions, contextual captions; teach spawn/base claim, main action, first collection/currency, upgrade and where rewards live. Keep instructions 1 objective at a time, include mobile support and a skip/replay option. Persist completion per user.
- Reward **one immediately useful limited-duration boost** after early tutorial completion. Label effect, duration, countdown and expiry; make it generous but not economy-breaking. Do not require purchase to complete onboarding.
- First session target: meaningful progress within 30–90 seconds; let player experience a themed reward reveal early. Do not make unsubstantiated retention promises.

## Collections, chance and restrictions
- Every game has **a theme-appropriate collection/index** (artifacts, toys, vehicles, creatures, etc.). Only add pets/eggs if explicitly in description or genuinely consistent with the game. If eggs are absent, provide an equivalent thematic acquisition system if needed.
- When chance exists, show true, server-defined probabilities as **1 in N** and/or percentages, including eligibility and modifiers. No fabricated odds, deceptive near-misses or undisclosed changes. Server determines rewards; client animates confirmed results.
- **NO PLAYER-TO-PLAYER TRADING**. No trade UI, chat-based transfer shortcut, swap, exchange, gifting disguised as trading, or accidental transfer endpoints. Personal inventories and collections only unless later explicitly overridden.

## Included universal systems (adapt to theme)
1. Daily rewards and login streaks with fair missed-day behavior and timezone/UTC-safe reset logic.
2. Daily + weekly quests; varied, achievable, objective progress sourced from server events.
3. Server and global leaderboards; anti-exploit validated stats, periodic refresh and pagination where needed.
4. Theme-fitting limited-time events; configuration-driven start/end and rewards; never invent a live event schedule.
5. Rare discovery server announcements; set meaningful thresholds, rate-limit and respect UI accessibility.
6. Rebirth/prestige if compatible with economy; clearly preview resets and permanent gains, with confirmation.
7. Redeemable promo codes; server-validated, case policy and one-redemption-per-user persistence.
8. Collection index/discovery book; seen vs owned states, rarity and completion progress.
9. Offline earnings **only when the game's core loop supports it**; capped accrual, clear rate calculation and anti-clock exploit safeguards.
10. Friends-playing-together bonuses; modest, transparent, cap stacking and server-authoritative eligibility.

## Data and engineering
- Server-authoritative currencies, drops, inventory, upgrades, purchases, base ownership and progression. Validate all remote calls, quantities and rate limits.
- Persist inventory, premium entitlements, battle pass progress/claims, tutorials, quests, codes, boosts, unlocks, index, base stages, rebirths and offline accrual; handle save retries, user leaves, server shutdown and schema migration.
- Mobile-first responsive GUI with safe areas and touch targets; desktop mouse, keyboard and gamepad considerations. Add accessible motion/sound options and avoid extreme flashing.
- Modular Luau architecture with single source of truth for configuration; stable asset naming, predictable folder structure, tests and logs. No unnecessary dependencies; verify any MCP operation and API support before using it.
- Do not hard-code live Robux product IDs, currency amounts, pass dates, prices, or odds; mark them as explicit CONFIG_REQUIRED values and expose previews with safe mock values.

## Standard expected delivery per generated game
1. `GAME_BRIEF.md` with name, description, loop, rewards, economy and decisions.
2. Blender source `.blend` and batch exports for the entire map and ALL custom 3D assets; material/texture assets included.
3. Figma UI system and game-specific screens, including preview states and UI test board.
4. Roblox Studio project / place with inspectable 6-base map in Edit mode, editor-visible UI previews, runtime GUI, scripts and assets.
5. `CONFIG.md` for products, prices, season dates, rarity tables and rewards; missing live values highlighted.
6. `QA_REPORT.md` with checks, screenshots/evidence where supported, bugs, missing setup and honest completion status.

## Quality gates
A feature is not **done** until visually inspectable, functionally interactive, tested with keyboard/mouse and touch where relevant, validated on server where security matters, and reviewed in Edit mode as well as runtime. `Previewed` is not `Tested`. No placeholders presented as final. No silent fallback from Blender to Studio modeling.
